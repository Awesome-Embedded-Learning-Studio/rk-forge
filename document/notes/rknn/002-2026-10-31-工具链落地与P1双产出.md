## 1. 工具链落地（坑与解）

| 坑 | 解 |
|---|---|
| Ghidra 12.2 嫌弃 JDK 21（12.x 最低 **JDK 25**） | `sudo apt install openjdk-25-jdk-headless`（25.0.4.1） |
| 无 TTY 时 analyzeHeadless 找不到 JDK | 每次带 `JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64` |
| 工程路径含 `.`（`.claude`）被 Ghidra 拒绝 | 工程放 `~/tools/rknn-ghidra/`，提取物仍落 `.claude/rknn/` |
| Ghidra 不自建工程目录 | 先 mkdir |
| PyGhidra 脚本未启用 Python | 改用 Java 脚本（原生即时编译零依赖）；两个 API 坑：`SymbolIterator` 不可 for-each、`getSignature()` 返回非 String 要 `.toString()` |
| dsh 是带工具的 agent，产出写它自己 cwd | 每单 prompt 钉死绝对输出路径（002 起已执行） |
| dsh prompt 走 argv 超 Linux 单参数 128KB 上限（E2BIG，exit 127） | 一律走 stdin：`dsh --profile headless - < task.md`；另发现 `--session-id` 可续会话 |

## 3. dsh-001 假设表（已验收）

- 产出：`dsh-001-api-ioctl-hypothesis.md`（441 行完整版）+ `dsh-001-summary.md`（摘要）
- **实证**：它给的六个 ioctl 号 `0xc0086440–0xc0206445` 与本地 `rknpu_ioctl.h` 的
  `DRM_COMMAND_BASE(0x40)+{ACTION,SUBMIT,MEM_CREATE,MEM_MAP,MEM_DESTROY,MEM_SYNC}` 逐条吻合——非编造
- 核心结论：真触内核的只有 init/run/create_mem(含 from_fd/from_phys)/destroy_mem/destroy + IO 的 MEM_SYNC；
  query/set_core_mask/set_io_mem 等是纯用户态状态管理。双设备路径假设：DRM render node（'d' magic 0x64）
  优先，备选 `/dev/rknpu`（'r' magic 0x72）
- strace 观察优先级：① init 全量分配图 ② run 的 SUBMIT 契约 ③ create/destroy_mem 配对 ④ flag 差分 ⑤ destroy 计数

## 4. dsh-002 静态标注结果（已验收，抽查实证）

- 产出 `dsh-002-static-annotation.md`（1159 行）；抽查 `rknn_run→FUN_0030d3f8(executor,3000)` 与
  decomp-002.c:2312 逐字吻合，非幻觉
- **核心发现：19 个导出入口全是薄壳，零 ioctl**——设备 I/O 全部下沉到后端 callee（0x2e/0x2f/0x30/0x33 区）
- 三层结构浮出：`0x50 句柄`（3 executor + mem 向量 + ThreadPool）→ `rknn::RKNNExecutor`（model/tensor/mem map/run-state）→ 后端
- 对 001 假设表的两条修正：`create_mem_from_fd` 只填结构体，真导入延迟到 `set_weight_mem`/`set_internal_mem`；
  `outputs_get` 本层无 wait/MEM_SYNC
- blob 本体是 C++（反编译见 `_Sp_counted_base`/`exception_ptr`）——与我们的 C++ 替代路线同构
- dsh 自报下一轮优先展开：`002eb400 / 002e3b20 / 0030d3f8 / 00307a30 / 00304e88 / 002ef368`

## 5. dsh-003 提交/导入路径结果（已验收）

- **ioctl 发射点全部找到（静态）**，产出 `dsh-003-submit-import.md`（569 行）：
  - 设备 open：`open("/dev/rknpu", O_RDWR)` 失败则 libdrm `drmOpen("rknpu")` → `/dev/dri/cardN`；
    全局单例默认 DRM 路径
  - SUBMIT：legacy `0xc0687201` / DRM `0xc0686441`，rknpu_submit 104B；发射点 `FUN_002e96f8`
  - MEM_CREATE：40B 版（驱动版本>799）`0xc0287202`/`0xc0286442`
  - fd 导入：DRM 先 `PRIME_FD_TO_HANDLE 0xc00c642e` 再 MEM_CREATE；legacy 直接 fd 当 handle
  - 常量算术已独立复核（104B=struct、'd'/0x2e/12B=PRIME），非编造
- **1.5.0 语义坑**：`create_mem_from_fd` 置 `mem_flags|=1`，直接传给 set_weight/internal_mem 会落入
  「别名/重查」无 ioctl 分支
- **3000ms 修正**：rknn_run 传的 3000 只进 FIRE 已完成分支；正常超时 = max(30×task 数, task_ctx+0x08)
- `FUN_002ef368` = `RKNNDevice::wait_fence_fd`（poll POLLIN + ETIMEDOUT/EINVAL 语义）
- 提交数据：task 数组 40B/项预建于 `task_ctx+0x1b0`，core_mask 取 `+0x754`，task_counter 内核回写
- **能力发现：dsh 会自驱 Ghidra**——发现本机 Ghidra 安装与工程后，自主导出了未提供的
  callees/device/submit 反编译（`decomp-003-{callees,device,submit,ctor2}.c`、`ghidra-devices.txt`）。
  协作模式升级：prompt 指方向+授权，材料它自己挖；Ghidra 地址 = ELF vaddr + 0x100000

## 6. dsh-004 init 分配图结果（已验收）

- 产出 `dsh-004-init-allocmap.md`（344 行）。**与 phhusson 日记对上了**：
  - init 第一件事就是开设备（`FUN_00181318` 单例 → `open("/dev/rknpu")` → 失败走 drmOpen）
  - init 内无 PRIME，全走 `MEM_CREATE(handle=0) → GEM_FLINK → HANDLE_TO_FD → MEM_MAP → mmap`
  - **静态单核最小可跑状态 = 6 个 GEM**（与 phpusson 观测一致）：init 内 4 次
    `weight(2)→regcmd(4)→task(10)→internal(2)` + 首次 inputs_set 惰性 +2（input/output）
  - 多核：RK3588 "v2" 且 core>1 时最多 3 executor，init 内 10 次 + I/O 共 12
  - 动态 shape 单子图：init 内 6 次 `weight→regcfg→context→regcmd→task→internal`
  - 六类对应：weight=权重；regcfg+regcmd=指令流；task(+task_unroll)=任务表；internal+context=工作内存
- **对 003 的修正**：`0x46495245`(ASCII "FIRE") 是 target 枚举 "v2"(RK3588) 的分派，不是「已完成」分支
  ——submit 链结论待复核（dsh-005 进行中）

## 7. dsh-005 提交链复核结果（P1 静态收官）

- 产出 `dsh-005-submit-recheck.md`（583 行）。完整提交链（每跳带 Ghidra 地址）：
  `rknn_run(0x172f78) → FUN_0030d3f8 → FUN_0030ac80 → FUN_004ad510(单核flush) → FUN_004b3d50
  → FUN_002f1140(新驱动)/FUN_002f1168(老驱动) → FUN_002e96f8/002e97d0 → ioctl(SUBMIT)`
- **新旧驱动双 ABI**：新 `0xc0687201`(legacy)/`0xc0686441`(DRM) 104B；老 `0xc0806441` **128B**
- rknpu_submit 字段偏移全解：flags+0 / timeout+4 / task_start+8 / task_number+0xc /
  task_obj_addr+0x18(IOVA) / core_mask+0x38 / fence_fd+0x3c
- task 数组 init 阶段由 v2 builder（`FUN_004b1250/002f1fc0/004b2520`）预建；run 只读
  `task_ctx+0x1b0`(IOVA)/`+0x28`(起始偏移)/`+0x10`(字节数,任务数=÷0x28)
- core_mask 唯一来源 `executor+0x754`（rknn_set_core_mask 写入；默认 0=AUTO；合法 0/1/2/3/4/7）
- **超时真相**：`max(30×task_number, 6000ms)`；rknn_run 传的 3000 在 v2 分支被直接丢弃
- `0x46495245`("FIRE") 全库 47 处分析完毕：全是 target 枚举 v2 分派，无「完成态」语义（003 修正坐实）
- 第 10 节 = 单 batch 单核提交最小伪代码 → C++ 引擎 driver client 的直接蓝本
