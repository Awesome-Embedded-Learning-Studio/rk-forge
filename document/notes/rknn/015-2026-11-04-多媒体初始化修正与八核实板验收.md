## 第一轮失败与修正

前轮 `media-multicore.AnIkFM` 中 RGA 已通过；启动检查、JPEG、H.264 失败。
这三项均收敛到用户态测试初始化/检查缺口，本轮没有修改或重刷内核。

1. 启动检查将 NPU 驱动名误写为小写 `rknpu`，真实 sysfs 名称为 `RKNPU`。
   修正为精确匹配，匹配失败时打印设备及期望驱动名，继续检查全部 23 个
   主副实例与 IOMMU，不放宽未绑定或 PM 同步失败的判断。
2. JPEG demo 设置 OUTPUT 后立即 REQBUFS，随后设置 CAPTURE JPEG。
   Hantro 的 CAPTURE 设置会重置 OUTPUT；已有 OUTPUT buffer 时返回 EBUSY。
   现先设置 JPEG CAPTURE，再设置 YUYV OUTPUT，两侧格式确定后才分配 buffer。
3. H.264 demo 只在 request 内设置 SPS/PPS，没有在分配前设置全局参数。
   `rkvdec_s_output_fmt()` 把 image_fmt 重置为 ANY，首次 SPS 应用需要确定
   YUV 格式；`rkvdec_s_ctrl()` 在 CAPTURE 已分配时返回 EBUSY。
   request setup 的错误又未由旧的驱动 run preamble 向上传递，可能继续使用
   默认参数解码。现按 stateless decoder 接口文档，依次执行 OUTPUT S_FMT、
   全局 S_EXT_CTRLS 设置 SPS/PPS/解码参数/矩阵、CAPTURE S_FMT、两侧 REQBUFS，
   每帧仍通过独立 request 设置参数。实板重跑确认像素与真值完全一致。

新增失败取证：在校验前保存 H.264 输入 slice、完整 capture allocation、
stride、bytesused、队列错误标志、worker/frame；打印首个差异坐标、实际值、
期望值和差异总数。即便出现 V4L2_BUF_FLAG_ERROR 也保留 capture 原始文件。
`analyze_decode.py` 可独立分析这些文件，不将错误缓冲区判为通过。
scalar 基线也记录各物理核心的前后计数与 IRQ。

## 主机回归与复查入口

`src/rknpu/rk3588/tests/host/test_media_demo.py`：实际 C demo 在模拟 V4L2 下接受三类正常输出，
拒绝三类损坏输出和 H.264 硬件错误，并验证失败帧/metadata 得以保存。
同一模拟驱动复现旧 JPEG EBUSY、旧 request-only SPS 的解码像素失败。
生产 demo 用 `-Wall -Wextra -Werror` 本机/交叉编译并通过 ELF 依赖预检。
`src/rknpu/rk3588/tests/host/test_boot_check.py` 验证大写 RKNPU、23 个绑定及缺失 IOMMU/PM pending
仍严格失败。套件 fixture 验证正常/空闲核心/新增错误三种判定。

```sh
PYTHONDONTWRITEBYTECODE=1 ~/tools/rknn-toolkit-venv/bin/python \
  src/rknpu/rk3588/tests/host/verify_media.py \
  out/rk3588-topeet/rootfs/opt/rknn-verify/results/media-multicore.OlwrQL

python3 src/rknpu/rk3588/tests/host/analyze_decode.py \
  out/rk3588-topeet/rootfs/opt/rknn-verify/results/media-multicore.OlwrQL
```

这是 128×128 固定输入、每核心 16 帧的功能与各组并发验收；不是吞吐极限、
长时间稳定性或所有编解码格式的覆盖性验收。
