## 1. NPU EBUSY 是资源描述重叠

0036 从 vendor 搬来的三块 NPU `reg` 各为 64 KB。其中 core0 的
`0xfdab0000..0xfdabffff` 包含已被独立 IOMMU 设备占用的
`0xfdab9000/0xfdaba000`；`devm_ioremap_resource()` 因此报告 EBUSY。
驱动随后无独占申请地 `devm_ioremap()` 回退，所以能够成功初始化和推理，
但资源描述仍然错误。

0039 把三个 CPU 控制窗口均限定为 `0x4000`，覆盖 PC、CNA、CORE 三类控制
bank，与主线 `rknn_core_0/1/2` 分别列出的 bank 相符。已核对 RK3588 路径
的控制寄存器访问包含 `0x1004/0x3004`，均在范围内；NPU 硬件命令流不通过
CPU 的 ioremap 窗口访问寄存器。IOMMU 保持独立资源归属。

正常的 `iommu is enabled, using iommu mode` 和 DRM 初始化信息保留。

内核提交 `575708c54`，补丁
`boards/rk3588-topeet/patches/linux/0039-arm64-dts-rk3588-topeet-fix-NPU-resource-overlap.patch`。

## 2. sync_state pending 是未绑定的消费者

该日志来自 `drivers/base/core.c:fw_devlink_dev_sync_state()` 的 strict 策略：
消费者尚未绑定，供应商仍需保留固件交接状态。PM-domain 的 `sync_state`
负责释放 stay-on 约束并按使用情况尝试断电；长期 pending 有实际状态意义，
不能只改 printk 等级或强制 `fw_devlink.sync_state=timeout`。

本地证据：

- 原 `.config` 中 `MEDIA_SUPPORT=m / VIDEO_DEV=m / VIDEO_HANTRO=m / RGA=m`，
  RKVDEC 和 VSI IOMMU 未启用；NFS rootfs 不存在 `/lib/modules`。
- 板级 fragment 虽写 `RGA=y`，但父层仍为模块，Kconfig 把它压回 `m`。
- 当前 7.3.1 源码的 OF 匹配表已有 VPU121、VEPU121、AV1、RGA2/3、
  RK3588 RKVDEC 和 Verisilicon IOMMU 支持。
- RGA、Hantro、RKVDEC 还明确拒绝同类第二个实例，返回 ENODEV，原因是
  尚无多实例调度支持。只补驱动后，这些副核心仍然未绑定。

处理：

1. 在 `boards/rk3588-topeet/kernel.config` 补齐 media 父层和 Hantro、RGA、
   RKVDEC、VSI IOMMU 内建配置，检查 olddefconfig 后仍为 `y`。
2. 0040 在本板 DT 中明确停用 RGA3 core1、VEPU121 1/2/3、RKVDEC1 及各自
   IOMMU。每类首个实例、RGA2 和 AV1 仍可用；未来驱动支持多核调度时再
   成对启用副核心。没有全局关闭多媒体设备。
3. 保持 fw_devlink strict 与 PM-domain 驱动逻辑；由真实驱动绑定解除等待。

内核提交 `a0c7eb0ac`，补丁
`boards/rk3588-topeet/patches/linux/0040-arm64-dts-rk3588-topeet-disable-secondary-media-cores.patch`。
两个新补丁已挂入 series；板级配置变更与 0040 配套。
