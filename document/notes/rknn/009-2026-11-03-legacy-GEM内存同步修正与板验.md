# 009 — legacy/GEM 内存同步修正（0038，首轮板验未通过）

后续真板取证已发现随机权重模型 FP16 下溢和 own 缺少 CPU 输出搬运；
用户已授权扩展到 own 修复及 ResNet18 非零验收，见
[010](010-2026-11-03-随机权重下溢与CPU输出搬运修正.md)。本文保留 0038 首轮记录。

内核提交 `0bcc4d771`，独立修正 0037 的同步适配；补丁
`boards/rk3588-topeet/patches/linux/0038-drivers-rknpu-fix-legacy-GEM-memory-sync.patch`
已加入 `series`。没有修改自研引擎或 vendor blob。

## 定位证据

- 旧板输出亲手复算：own/vendor 各 2000 字节、各 **0/1000 非零**，两者
  **并非 byte-exact**。这只是修复前基线，不能拿来证明新内核通过。
- `rknpu_gem_sync_ioctl()` 要求创建标记带 CACHEABLE；legacy DMA_HEAP
  同步接口没有此限制。动态记录的 regcmd 创建标记为 `0x5`
  （NON_CONTIGUOUS | WRITE_COMBINE），会被 DRM 的检查拒绝。
- 自研 `Driver::mem_sync()` 固定传 `obj_addr=0`，使用 `2=TO_DEVICE`、
  `1=FROM_DEVICE`，调用者还忽略返回值。内核定义实际是 **1=TO_DEVICE、
  2=FROM_DEVICE**。因此只移除 CACHEABLE 检查不足以修复 own。
  权重、输入、输出的创建标记 `0x3` 本来已有 CACHEABLE。
- `rknpu_gem_object_create()` 内部已有 IOMMU domain 切换与 put；
  `rknpu_submit()` 对 PC 且非 NONBLOCK 作业调用 `rknpu_job_wait()`。
  `fence_fd=-1` 本身并不是内核是否等待的判断条件。
- vendor init 的 sync 日志支持继续查同步路径，但它报告的 errno=2
  不是这里返回的 EINVAL，不能仅据该行断言所有全零现象的根因已证实。

## 修改与限制

1. 抽出 `rknpu_gem_object_sync()`，复用原有 DMA 同步、SG/SRAM/NBUF
   处理及 domain 切换；DRM ioctl 保留原 CACHEABLE 门槛。
2. legacy MEM_SYNC 从本会话查找对象，再校验方向与范围；绕过 DRM 的
   CACHEABLE 门槛。零长度的合法范围直接成功，空指针、跨会话对象、
   越界或溢出范围返回 EINVAL，不解引用未校验的用户地址。
3. legacy SUBMIT 前向 device 同步整个会话；成功完成阻塞 PC 作业后向
   CPU 同步整个会话。这样不改用户态也能覆盖 own 无效同步导致的缓存
   所有权缺口，不按大小或调用顺序猜测 `obj_addr=0` 属于哪个 buffer。
   无效 MEM_SYNC 仍失败；此修改没有修正 own 的用户态 ABI 实现。
4. 会话 mutex 串行化 ioctl，防止遍历和提交期间对象被另一线程销毁。

全会话同步会增加每次提交的缓存维护开销，本轮优先验证正确性。
NONBLOCK 路径不在返回时同步回 CPU，客户端仍须等待完成后显式同步。
0038 首轮真板的非零输出与双侧 byte-exact 均未通过，见下文。

## 用户上板操作

手动用 TFTP 加载新 Image 后，在板上执行：

```sh
cd /opt/rknn-verify
sh ./verify_legacy_sync.sh
```

脚本源文件 `src/rknpu/rk3588/tests/board/verify_legacy_sync.sh` 已复制到 NFS rootfs。
它先执行原 `./run.sh models/mobilenetv2_fp.rknn`，然后用同一 harness
双跑到新的 `results/legacy-sync-0038.XXXXXX/`，保留原始 `out0.bin`。
检查每侧恰好 2000 字节、1000 个 fp16 中非零数 >900、全部有限，
并验证 own/vendor byte-exact。由于原 `run.sh` 成功会删除输出，额外
双跑是为了保留可复核的验收证据。脚本也保存内核版本、日志与 dmesg。

请贴回脚本输出及新证据目录的 `dmesg.log` 中 rknpu/IOMMU 相关行。
脚本只能由用户在板上手动运行；本次未连接、重启或烧写板卡。

## 0038 首轮真板结果与下一轮取证

证据目录 `results/legacy-sync-0038.1RhjDu/`，内核版本
`7.3.1-00023-g0bcc4d771afc`。用户手动上板执行，主机直接读取共享文件复核：

- own/vendor harness 都 exit=0，但各 **0/1000 非零**，输出间仍有
  **494 字节差异**，均为零的符号位；这轮 **FAIL**。
- vendor init 的 `failed to sync memory` 日志已经消失，说明修正了一个
  可见错误，但还不能解释或解决全零结果。
- 完整 dmesg 没有新增 job timeout/reset 或 IOMMU fault。
- EBUSY 对应 NPU core0 的 `0xfdab0000..0xfdabffff` 资源与其中的
  IOMMU `0xfdab9000/0xfdaba000` 资源重叠。现有 probe 对 EBUSY
  使用 `devm_ioremap()` 回退，随后 DRM 初始化成功；该行本身不是
  probe 失败或 NPU 未执行的证据，不能据它断言全零原因。
- 原脚本依赖 Python，但实际 rootfs 是 BusyBox 环境，没有 Python。
  已改为 `od/awk/cmp`，无需安装 Python；主机样本测试验证正负零、
  Inf/NaN、900/901 非零门槛及 byte-exact 判断。

暂不追加推测性内核修补。独立诊断库 `legacy_trace.so` 已交叉编译并部署，
在 `LD_PRELOAD` 下转发原有 ioctl/mmap/munmap，不改参数、不代做同步、
不修改引擎和 vendor 文件。主机模拟验证了参数、返回值与 errno 保持，
以及提交前后快照内容。AArch64 产物通过零警告编译并检查 rootfs libc 依赖；
真实板上的动态加载仍待用户运行验证。

**无需重启或更换 Image**，在当前内核上执行：

```sh
cd /opt/rknn-verify
RKNN_TRACE=1 sh ./verify_legacy_sync.sh
```

新证据目录会保存双侧 ioctl 参数/返回值日志、提交前后每个已跟踪 dma-buf
映射的快照、`interrupts.before/after` 与 dmesg。下一步根据这些文件确认
权重/输入是否已写入、输出的原生 buffer 是否变化、实际提交的任务与 core
是否一致及 IRQ 是否增加，再决定是否需要补内核诊断。

## 若仍失败

- 先核对 `kernel.txt` 中版本是否含 `0bcc4d771`，排除旧 TFTP Image。
- 核查同一新目录中双侧日志和输出，不读取旧的 `mobilenetv2_fp.`。
- 若仍全零：收集完整 dmesg 中 job timeout/reset、IOMMU fault 和
  submit 的完成状态；必要时下一轮仅加内核诊断，记录 create 标记、
  sync 对象/方向/范围/返回码及任务完成计数。不能只按 exit=0 判通过。
- 若输出已非零但不同：保留两个 bin，统计差异位置，再用 host ONNX
  真值区分数值偏差与装配/布局问题；不要把输出不一致归咎于缓存而
  直接扩大修补。
