# 010 — 全零原因复核与 own CPU 输出搬运修正

0038 第二轮真板取证表明，不能用随机初始化 MobileNetV2 的全零 FP16
输出认定缓存同步失效。用户已明确授权修正 own，并增加非零模型验收。
内核继续使用 `0bcc4d771`，这轮没有追加推测性内核改动。
新 own 已在 `results/legacy-sync-0038.jr4FZz/` 真板验收通过：MobileNetV2
双侧 0/1000 非零、有限且 byte-exact；ResNet18 双侧 1000/1000 非零、有限且
byte-exact。两模型的原 `run.sh` 也各 1/1 PASS，主机已复读原始 bin 确认。

## 1. 真板证据

目录 `results/legacy-sync-0038.v72Q5b/`，来自用户手动运行取证脚本：

- 四次推理对应 core0 共享 IRQ 计数从 0 增至 4；未出现 timeout/reset/IOMMU fault。
- 六块 buffer 在 own/vendor 提交前分别逐字节一致，提交后也分别逐字节一致。
- internal 从全零变为 **1,073,429 个非零字节**，CPU 已读到 NPU 写回数据。
- NPU 实际分类输出位于 internal 的 `0xa00`。vendor 在提交后将其搬至
  用户输出 buffer；vendor 最终 2000 字节与该原生区域 **逐字节一致**。
- own 原实现缺少该步，一直读取从未写入的另一块 output GEM，因此全 +0；
  vendor 原生结果含 -0，两者相差 494 个符号位字节。

## 2. 为什么不能继续要求此 MobileNet 非零 >900

模型生成脚本 `scripts/convert_mobilenetv2.py` 明确采用随机初始化权重。
用现有 ONNX 和同一输入 `fp16 0x5555 = 85.3125` 亲手重跑 CPU 真值：

| 模型 | FP32 最小值 | FP32 最大值 | 转 FP16 后非零数 |
|---|---:|---:|---:|
| mobilenetv2_fp | -2.1971292e-8 | 2.3796387e-8 | **0/1000** |
| resnet18 | -330.73758 | 292.05945 | **1000/1000** |

FP16 最近偶数舍入的归零阈值为 `2^-25 = 2.9802322e-8`；这个 MobileNet
的所有 FP32 输出绝对值都低于该阈值。CPU FP32 输出直接与零向量算余弦，
不能证明驱动有错。中间 FP16 舍入也可能改变最后零的符号，不能要求其符号
和 FP32 最后一步转 FP16 完全一致；own/vendor 同配置仍须 byte-exact。

复核命令：

```sh
PYTHONDONTWRITEBYTECODE=1 ~/tools/rknn-toolkit-venv/bin/python \
  src/rknpu/rk3588/tests/host/analyze_sync.py \
  out/rk3588-topeet/rootfs/opt/rknn-verify/results/legacy-sync-0038.v72Q5b
```

报告含模型 SHA-256，已保存至
`out/rk3588-topeet/rknpu-output-fix/host-evidence-analysis.json`。

## 3. own 修改

- `model.h / loader.cpp`：解析 op 的 f1 类型、f4/f5 输入/输出张量下标。
- `shell.cpp`：成功同步提交后，执行没有 NPU 模板的终端 CPU Reshape。
  按图内张量索引定位 internal 区域，按逻辑 NCHW 顺序去掉 NC1HWC2 的通道
  padding，写入二维分类输出；源区间/目标大小校验并传播同步错误。
  MobileNet 的源偏移解析为 `0xa00`，ResNet18 为 `0x400`，没有硬编码偏移。
- `driver.cpp`：MEM_SYNC 使用实际 `obj_addr`，方向改为内核定义的
  `1=TO_DEVICE / 2=FROM_DEVICE`；MEM_DESTROY 回填实际对象地址。

支持范围是本轮已实证的同 dtype fp16/int8、NC1HWC2 → 二维终端 Reshape；
没有声称支持任意 CPU fallback 算子或所有输出形状。
