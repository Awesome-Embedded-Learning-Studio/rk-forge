## 范围与实现

| 类别 | 物理实例 | 用户入口 | 并发方式 |
|---|---:|---|---|
| RGA3 | 2 | 一组 V4L2 frontend | 两路独立会话 |
| VEPU121 JPEG 编码 | 4 | 一组 V4L2 frontend | 四路独立会话 |
| RKVDEC | 2 | 一组 V4L2 frontend | 两路独立视频流 |

0041（`94b2c1897`）新增共用核心池，替换三个驱动原先拒绝其他同类实例的
逻辑。打开 frontend 时，驱动选择已就绪且打开会话数最少的物理核心；
相同会话数时轮转。选择发生在命令与视频 buffer 分配之前。

会话保持核心亲和性，直到关闭：每个核心保留独立 M2M 队列、DMA 分配设备、
IOMMU 映射、寄存器、IRQ、既有 watchdog 和 runtime PM。解码参考帧也始终
属于同一设备。frontend 与队列 ioctl 的锁保持一致，硬件作业由各核心队列
执行；仅主实例注册 video/media 用户入口，后端仍使用该 media device 的
request API。设备链接保证正常卸载时先拆后端再拆 frontend。

这轮提供**多会话并行**，没有实现单帧跨核拆分或运行中迁移。分配依据是
打开的会话数量，性能还受实际任务长度、共享带宽等影响；不能仅据核心数量
宣称单路处理速度翻倍。

0042（`4fad778b0`）撤销 0040 的临时 DT 禁用，恢复全部 RGA3×2、VEPU121×4、
RKVDEC×2 以及各自 IOMMU。保留 0039 的 NPU 资源范围修正和内建驱动配置。
这两个新补丁已加入 board series。

## 可观测性与错误路径

每个物理设备提供只读属性，ABI 说明随 0041 提交：

```text
m2m_core_users
m2m_core_submitted
m2m_core_completed
m2m_core_errors
```

未完成 probe 的后端不会加入池；次实例等待 frontend 就绪；打开失败会归还
会话计数。保留现有 IRQ/watchdog 完成机制，并补齐 Hantro 作业启动失败时
的 clock/runtime-PM 引用回收。启动日志的“绑定成功”不作为处理任务成功的
验收依据。

## Demo

源文件在 `src/rknpu/rk3588/tests/board/multicore/`，已部署到
`/opt/rknn-verify/multicore/`。不要求板上安装 Python、FFmpeg 或 v4l2-ctl。

每组先跑单会话基线，再让所有 worker 都打开同一 frontend、完成 buffer
准备后，通过 pipe barrier 同时开始并发测试。默认每路 16 帧：

- RGA3：两路不同的 RGBA 图案，逐帧检查 identity blit 像素完全一致。
- JPEG：四路不同的 YUYV 图案，编码质量 90，板上检查返回状态、SOI/EOI 和
  长度，并各保存一张 JPEG；主机用 Pillow 解码、核对尺寸与各自图案，
  要求 PSNR ≥28 dB，防止仅有合法 JPEG 头或全黑图也被算作成功。
- RKVDEC：两路不同的固定 H.264 baseline IDR/I_PCM 帧，通过 stateless
  request API 解码；逐像素核对 NV12 的亮度与色度。

IDR 样本由 `make_idr.py` 生成，未使用来源不明的测试视频。已用独立的
OpenCV/FFmpeg 软件解码器解码两路样本，与原 NV12 转 RGB 的参考最大误差
均为 1。硬件解码端仍要求原生 YUV 精确匹配。

并发阶段按核心分别要求：提交增量和成功完成增量均等于帧数、错误增量为
0、IRQ 计数增加、测试后打开会话数回到测试前。所有核心均须满足条件。
另保留处理后的原始图像，主机复核 RGA/H.264 像素，而不是只相信日志。
最后重跑 MobileNetV2 与 ResNet18 的 NPU 回归。

## 板上操作

手动重新 TFTP 加载 **Image 和 rk3588-topeet.dtb 两者**。当前版本：
`7.3.1-00027-g4fad778b0c5a`。本次未连接、重启或烧写板卡。

```sh
cd /opt/rknn-verify/multicore
sh ./run.sh
```

脚本输出 `Evidence: /opt/rknn-verify/results/media-multicore.XXXXXX`，保存驱动
绑定、PM 状态、每组单路/并发日志、逐核心计数、中断、输出文件与 dmesg。
`DEVICE PASS` 代表板端操作和检查通过，JPEG 像素仍须由主机复核。

用户贴回结果后，主机运行：

```sh
PYTHONDONTWRITEBYTECODE=1 ~/tools/rknn-toolkit-venv/bin/python \
  src/rknpu/rk3588/tests/host/verify_media.py \
  out/rk3588-topeet/rootfs/opt/rknn-verify/results/media-multicore.XXXXXX
```

本轮已按上述流程将八核处理验收记为 PASS。后续单路基线失败时保留日志并跳过对应并发
阶段，先解决基础 codec 路径；并发失败时结合逐核错误、IRQ 与不同图案的
输出定位，不用降低判断门槛替代修复。
